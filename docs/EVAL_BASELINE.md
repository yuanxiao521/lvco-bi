## 1. 先修了评测器自己的三个系统性偏差

> 不修这三个，「基线」就是在测判分器，不是在测产品。三处修正都让数字**变严或变准**。

| # | 偏差 | 表现（修前） | 修正 |
|---|---|---|---|
| 1 | 判分器把**第一个**数据源当表引用，且硬编码只替换 `ecommerce_orders` | 用 A 表跑 B 表 SQL → `Binder Error`，SQL 准确率恒 0 | 按题目 `expected_datasource` 匹配 + 所有表名参与替换（长名优先） |
| 2 | 图表类型用**字符串全等**比较 | `donut` vs `pie`、`horizontal_bar` vs `bar` 被判错 → 50% | 引入等价类（pie/bar/line/kpi…）；**grouped_bar 与 stacked_bar 仍不等价** |
| 3 | 期望模板返回 0 行仍计入分母 | 模板用 `now()-30day`，演示数据是历史快照 → 把「数据过期」记成「模型算错」 | 新增 `sql_scorable`：期望为空 → 不计入 SQL 分母，单列 `expected_empty(unscorable)` |

修正前后同一批结果：SQL **3/12 → 2/9 (22.2%)**（更严），图表 **6/12 → 9/12 (75%)**（更准）。

## 2. 失败分类（12 题逐条）

| 题 | SQL | 图表 | 期望→实际 | 归因 |
|---|---|---|---|---|
| Q001 (kpi) | ✅ | ✅ | kpi_card→kpi_card | — |
| Q002 (trend) | — | ✅ | line→line | 期望模板 0 行（`now()-30day`），不可评分 |
| Q003 (distribution) | ❌ | ✅ | pie→donut | 图表等价已判对；SQL 口径不同 |
| Q004 | ❌ | ✅ | bar→horizontal_bar | 同上（朝向变体已判对） |
| Q005 | ❌ | ❌ | grouped_bar→stacked_bar | **真错**：分组 vs 叠加是不同信息结构 |
| Q006 | ❌ | ✅ | line→line | 结果集同 13 行但值不同 → 时间窗/阈值口径差 |
| Q007 | ❌ | ✅ | bar→bar | SQL 结果不一致 |
| Q008 | ❌ | ❌ | line→bar | **真错**：趋势题选了柱状图 |
| Q009 | ✅ | ✅ | kpi_card→kpi_card | — |
| Q010 | ❌ | ✅ | bar→horizontal_bar | 结果集同 5 行但值不同 |
| Q011 | ❌ | ❌ | grouped_bar→pie | **真错**：对比题选了饼图；输出还缺关键词 |
| Q012 | ❌ | ✅ | bar→bar | 4 行 vs 5 行 → 过滤条件差 |

**归纳成三类**：
1. **数据集模板过期（3 题）**：Q002/Q005/Q008 的 `expected_sql_template` 用 `now()` 相对窗口，演示数据是历史快照 → 期望为空。应把模板改成锚定数据最大日期（`(SELECT MAX(order_date) …)`）。
2. **口径差异（4 题）**：Q006/Q007/Q010/Q012 —— 行数接近或相同但值不同，典型是时间窗/过滤条件/聚合口径。属于**语义层**该管的范围（指标口径未强制）。
3. **图表选择错误（3 题）**：Q005/Q008/Q011 —— 分组对比选成叠加、趋势选成柱状、对比选成饼图。正是**数据画像（基数/分布）**与选图规则该解决的。

## 4. 环境与可复现性

- 模型：`glm-5.3-flash`，走本机代理 `127.0.0.1:8788`；**单次调用 30–190s 波动很大**，基线耗时主要花在报告生成那一次调用上。
- 数据集：`dataset.jsonl` 33 题，本次跑前 12 题；账号 `eval@lvco.bi`（`21bee02f…`），数据源 `ecommerce_orders` / `product_performance`。
- 单题硬超时 480s；结果**逐题落盘**（`eval_results.jsonl`），进程被打断也能保住已完成部分。
- 重判分（不重跑 LLM）：`backend/scripts/rejudge_eval.py` —— 用已存的 `*_events.jsonl` 重新判分，改判分规则时用它，省一次 27 分钟。
