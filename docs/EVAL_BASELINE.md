## 1. 先修了评测器自己的五个系统性偏差

> 不修这些，「基线」就是在测判分器。五个修正全部让数字**更严或更准**，方向不一致但都更可信。

| # | 偏差 | 表现 | 修正 |
|---|---|---|---|
| 1 | 判分器取**第一个**数据源当表引用 | 用 A 表跑 B 表 SQL → `Binder Error`，SQL 恒 0 | 按题目 `expected_datasource` 匹配 |
| 2 | 表名替换**硬编码**成 `ecommerce_orders` | 其他表名原样发下去 → 报错 | 所有数据源名参与替换（长名优先） |
| 3 | 只看 `query_sql` 的 SQL 文本 | **query_engine 结构化取数完全没被测**（3 题被误判失败） | 增加 `_extract_agent_rows`：直接比对 Agent 实际查出的行 |
| 4 | 图表类型**字符串全等** | `donut` vs `pie`、`horizontal_bar` vs `bar` 判错 | 引入等价类；**grouped_bar 与 stacked_bar 仍不等价** |
| 5 | 期望模板用 `now()` 相对窗口 | 演示数据是静态快照（2025-08 ~ 2026-08），「最近30天」= 0 行 → 把「数据过期」记成「模型算错」 | **判分期**把 `now()` 锚定到 `(SELECT MAX(order_date) …)`（期望 SQL 与 Agent SQL 同时锚定，保证公平）；**冻结数据集本身一个字节都没改** |

**修正过程本身就是结论**：SQL 准确率 **22% → 25% → 50%** 的三次跳变，**没有一次改了产品代码**——全是判分器在纠正自己。这提醒一件事：**没有可信评测时，任何"优化"都无法证明有效**。

> **关于冻结测试集（重要，自我纠正）**：
> 第一次修第 5 条偏差时，我**直接改了 `dataset.jsonl` 的 8 条模板**（把 `now()` 换成锚定子查询）并提交了。
> 这违反"测试集冻结"的前提——数据集是**标尺**，标尺不能为了跑出好看的数字去改。
> 已撤销：`dataset.jsonl` 与改动前**逐字节一致**（`git diff 96b6005^ HEAD` 为空），
> 锚定逻辑移至判分器的执行器里（`build_sql_executor.exec_sql`）。
> 重判分验证：v1/v2/33 题的数字与改动前**完全一致**（说明当时改数据只是等价变换，但做法是错的）。

## 2. 失败分类（12 题逐条）

| 题 | SQL | 图表 | 期望→实际 | 归因 |
|---|---|---|---|---|
| Q001 (kpi) | ✅ | ✅ | kpi_card→kpi_card | — |
| Q002 (trend) | ✅ | ✅ | line→line | 锚定后通过 |
| Q003 (distribution) | ✅ | ✅ | pie→donut | 等价类判对 |
| Q004 | ✅ | ✅ | bar→horizontal_bar | 等价类判对 |
| Q005 | ❌ | ❌ | grouped_bar→stacked_bar | **约束没听懂**：问「华东 vs 华北」，它对比了全部 7 个地区（期望 2 行 / 实际 7 行） |
| Q006 | ❌ | ✅ | line→line | 同样 13 行但值不同 → 时间窗/阈值口径差 |
| Q007 | ❌ | ✅ | bar→bar | 同样 5 行但值不同 |
| Q008 | ❌ | ❌ | line→bar | 8 行 vs 7 行 → **边界 off-by-one**（最近7天含端点）+ 趋势题选了柱状图 |
| Q009 | ✅ | ✅ | kpi_card→kpi_card | — |
| Q010 | ❌ | ✅ | bar→horizontal_bar | 同样 5 行但值不同 |
| Q011 | ✅ | ❌ | grouped_bar→pie | SQL 对但选了饼图（对比题）；输出还缺关键词 |
| Q012 | ❌ | ✅ | bar→bar | 4 行 vs 5 行 → 过滤条件差 |

**归纳成三类**：
1. **约束没听懂（1 题）**：Q005 —— 用户点名两个地区，它做了全量对比。这是**指令遵循**问题，不是 SQL 能力问题。
2. **口径/边界不一致（4 题）**：Q006/Q007/Q010/Q012 + Q008 的 off-by-one —— 时间窗含不含端点、过滤条件、聚合口径。这一类**只能靠语义层（指标口径）+ 口径确认**解决。
3. **图表选择错误（3 题）**：Q005/Q008/Q011 —— 分组对比选成叠加、趋势选成柱状、对比选成饼图。正是**数据画像（基数/分布）+ 选图规则**该解决的。

## 4.5 第一次 A/B：提示词规则改动（v1 → v2）

改动：chat 画像加三条规则（出图前看数据形态 / 点名条件必须筛选 / 口径说出口）。
同一 12 题、同一账号、同一模型，改动前后各跑一次：

> 注：判分器后来修了第 6 个偏差（见下），下面这组数字是**同一判分规则下重判**的结果，可比。

| 指标 | v1（基线） | v2（加规则） | 变化 |
|---|---|---|---|
| **SQL 准确率** | 5/12 (41.7%) | **6/12 (50%)** | **+1** |
| **图表类型正确率** | 9/12 (75%) | **10/12 (83.3%)** | **+1** |
| 输出有效率 | 12/12 | 12/12 | = |
| 工具成功率 | 12/12 | 12/12 | = |
| 平均迭代 | 6.83 | 7.83 | +1（多做画像与核对，成本上升） |

**第 6 个判分器偏差（本轮修掉的）**：`_extract_agent_sql` 取的是"最后一条 query_sql 文本"，
不看它**是否成功**。Agent 常见"先查 gross、再试 net"的模式，第二次被 guard 拦下 →
判分器拿**失败的意图**去和期望比，把一次成功查询判成失败（Q001 就是这样）。
改为"只取最后一次**成功**的查询"后，v1 的 SQL 从 6/12 回落到 5/12（说明之前那 1 分是虚高）。

**逐题变化（这是关键，不是总分）**：
- ✅ **Q005**：grouped_bar→**grouped_bar**（原先是 stacked_bar）——"对比用分组不用叠加"这条规则**精准命中**；且筛选从"7 个地区"缩到 4 个（期望 2，仍有差距）。
- ✅ **Q008**：bar→**line**——"趋势题用折线"命中。
- ❌ **Q007**：bar→**donut**——新规则"占比题用饼图"被**过度套用**（这题不是占比题）。规则需要加限定条件。
- ⚠️ **Q001/Q002**：v1 通过、v2 不通过，但**行数相同、值不同**（Q001 1 行 vs 1 行、Q002 30 行 vs 30 行）→ 属于**同一次运行内的口径/取整差异**，不是提示词直接导致。

**结论（诚实）**：
1. 两条被点名的图表错误**确实修好了**，说明"用失败样本写规则"这条路径有效；
2. 但 **n=12 太小**，+1/−1 都在噪声范围内，**不能声称整体提升**；
3. SQL 没有改善，说明"口径"不是提示词能解决的，得靠语义层；
4. 出现一次规则**过度套用**（Q007），说明规则要写"适用条件"而不只是"结论"。

→ 因此下一步改成：**先跑 33 题拿稳定基线**，再谈优化对比；规则补"只在占比语义明确时才用饼图"。

## 4.7 语义达成率（**主指标**，semantic_judge + dataset_v2）

> 执行准确率（上文 4.x）是"内部回归尺"，**对外的产品 KPI 是语义达成率**。
> 两者差 30+ 个百分点不是矛盾，是在问不同的问题：执行准确率要求"算出同一张结果表"；
> 语义达成率按 6 个维度判"期望语义 ⊆ 实际查询语义"（口径/维度/过滤/排序/图表/要点）。

**结果（30 题，有效 26 题，总耗时 3476.9s）**

| 项 | 值 |
|---|---|
| **平均语义达成率** | **95.0%** |
| 全部子项达成的题 | 19/26 |
| 历史对照 | 90–100%（同档，**没有退步**） |

| 子项 | 达成/可判 | 达成率 |
|---|---|---|
| 指标口径 | 24/26 | **92%** |
| 维度/粒度 | 3/4 | 75% |
| 过滤/时间口径 | 2/2 | 100% |
| 排序限量/块数 | 1/1 | 100% |
| 图表类型 | 25/26 | **96%** |
| 回答要点/叙事 | 24/26 | 92% |

**4 道运行失败（已从分母剔除）**：V004 / V008 / V009（对话 150s 超时）、P007（画布 360s 超时）。
这正是为什么必须补 `run_error` —— 不剔的话 95% 会被算成 **86.3%**。

**本次顺带修掉的评测器缺陷**
1. 语义报告的子项分母是"details 里出现过这个词"，出现过 `13/10 = 130%` 的荒谬数字 →
   改为按行判定（`期望无…` 不计入分母、✓/✗/缺失 分别计）；
2. 运行失败题此前会计入总分与路径分组 → 现在单独标注并剔除；
3. `semantic_run_eval.py` 在 GBK 控制台打印 `✓` 直接抛 `UnicodeEncodeError` 中断整轮 →
   已 `stdout.reconfigure(utf-8)`（这也是它长期跑不稳的原因）。

**剩余 7 道未满分题的真实短板**
| 题 | 分数 | 短板 |
|---|---|---|
| V002 / V003 | 0.83 | 走了 raw_sql，**没引用指标语义层**（缺 customer_count / avg_price） |
| V010 | 0.83 | 维度粒度：期望 `order_date@quarter`，给了 month |
| V017 | 0.80 | 画布未用 `update_chart_block` |
| V018 / P002 | 0.80 | 画布回答缺要点（"折线/按月""季节"） |
| P010 | 0.80 | 画布图表类型缺失 |

→ 下一步优先级：**指标语义层接入工具面**（补 V002/V003）、画布收尾补齐要点。
